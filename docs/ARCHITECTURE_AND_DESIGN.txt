WORKFLOW AGENCY ARCHITECTURE AND DESIGN
=======================================

Document date: 2026-06-28
Project type: Django, HTML, Bootstrap, vanilla JavaScript, PostgreSQL, Cloudinary, M-Pesa
Primary target users: mobile-first users in Kenya
Primary admin goal: manage online jobs, referrals, deposits, withdrawals, and business solvency


1. EXECUTIVE SUMMARY
--------------------

Workflow Agency is a web platform where users can register, activate their account through M-Pesa, complete admin-managed jobs, earn approved rewards, invite referrals, buy/access products, and request withdrawals. The design is based on the sample UI, which shows a dark dashboard with wallet cards, referral tracking, product store, task categories, finance pages, and user profile pages.

The most important architectural rule is this:

Money shown in a user's wallet is a liability until it is spent, reversed according to written terms, or withdrawn. Admin revenue reports must never confuse wallet balances with company profit.

This is especially important because the activation fee is intended to appear in full as the user's starting balance. If the full activation amount is withdrawable, the business must keep enough cash reserve to pay it. If the activation amount is only a platform credit, the UI and terms must state that clearly.

4. USER ROLES
-------------

Guest:

- Can view public landing/login/register pages.
- Can register with username, phone number or email, password, and optional referral code.

Locked user:

- Has registered but has not activated.
- Can view activation instructions and payment page.
- Cannot claim jobs, withdraw, access paid products, or earn normal rewards.

Active user:

- Has completed activation.
- Can use dashboard, jobs, referrals, wallet, products, profile, and withdrawal request pages.

Flagged user:

- Account is active but restricted by fraud checks or admin action.
- Can view account but cannot withdraw or claim selected jobs until reviewed.

Suspended user:

- Cannot login or cannot perform earning actions, depending on admin setting.

Staff reviewer:

- Reviews submitted job proof, approves/rejects rewards, handles support tickets.

Finance admin:

- Manages deposits, withdrawals, reconciliation, finance reports, payout approvals, and finance settings.

Super admin:

- Full access to users, settings, jobs, wallet adjustments, M-Pesa settings, roles, and audit logs.

10. ACTIVATION FLOW
-------------------

Required behavior:

- When a user joins, account features are locked.
- User must pay the minimum activation fee set by admin.
- If the user was referred, a configured referral bonus goes to the referrer.
- The activation fee shows in full in the new user's account balance as a starting point.

Safe implementation flow:

1. User registers.
2. User status is LOCKED and activation status is NOT_ACTIVATED.
3. User opens activation page.
4. System creates ActivationPaymentRequest.
5. User pays via STK Push or C2B.
6. M-Pesa callback is received.
7. System verifies amount, phone, reference, and duplicate status.
8. System marks activation payment confirmed.
9. System changes user status to ACTIVE.
10. System posts ACTIVATION_CREDIT to the user's wallet.
11. If a valid referrer exists, system posts REFERRAL_BONUS_PENDING or REFERRAL_BONUS_AVAILABLE according to admin rules.

Important:

If KES 185 is paid and KES 185 is credited to the user's wallet, then KES 185 is still owed to the user unless it is non-withdrawable platform credit. If the referrer also earns KES 75, the business has created KES 260 in user-visible value from KES 185 cash. That can only be safe if KES 75 is funded from real revenue or marketing budget.

13. SUGGESTED JOB TYPES AND PAYOUT RULES
----------------------------------------

All payout amounts must be admin-configurable. The values below are starting suggestions only.

1. Survey jobs

- Suggested reward: KES 10-150.
- Rule: pay after all required questions are answered and duplicate checks pass.
- Proof: survey response.
- Risk: low quality/duplicate answers.
- Controls: one response per user, device/IP checks, attention-check questions.

2. Watch ads/video

- Suggested reward: KES 0.50-5 per verified view.
- Rule: pay only after timer completes and page remains active.
- Proof: system event log.
- Risk: bots and very low real ad revenue.
- Controls: daily cap, cooldown, random checks, no payout above actual ad revenue.

3. Trivia/quiz

- Suggested reward: KES 2-20.
- Rule: pay after user scores above admin pass mark.
- Proof: quiz answers and score.
- Risk: answer sharing.
- Controls: random question order, question banks, cooldown.

4. Blogging/social share

- Suggested reward: KES 5-40.
- Rule: pay after submitted URL/screenshot is approved.
- Proof: URL, screenshot.
- Risk: deleted posts and spam.
- Controls: minimum post age before approval, manual review.

5. App/game testing

- Suggested reward: KES 50-300.
- Rule: pay after user submits useful report with screenshots.
- Proof: screenshots, device model, bug report.
- Risk: fake reports.
- Controls: report quality checklist and reviewer scoring.

6. Website feedback/usability

- Suggested reward: KES 50-250.
- Rule: pay after user completes checklist and feedback is accepted.
- Proof: answers, screenshots, session metadata.
- Risk: copy-paste feedback.
- Controls: minimum character count, unique answer checks.

7. Data entry/tagging

- Suggested reward: KES 2-25 per batch.
- Rule: pay after required accuracy threshold is met.
- Proof: submitted batch.
- Risk: low accuracy.
- Controls: gold-standard validation records and random review.

8. Transcription

- Suggested reward: KES 20-100 per short clip.
- Rule: pay after text accuracy is reviewed.
- Proof: transcript.
- Risk: poor quality.
- Controls: reviewer scoring and rejection reasons.

9. Translation

- Suggested reward: KES 20-200 per task.
- Rule: pay after translation is reviewed.
- Proof: translated text.
- Risk: machine translation abuse.
- Controls: quality scoring and random audits.

10. Product review

- Suggested reward: KES 20-100.
- Rule: pay after review is approved and user is eligible.
- Proof: review text or screenshot.
- Risk: fake reviews.
- Controls: require actual purchase/access, content rules.

11. Paid chat sessions

- Suggested reward: KES 20-150 per approved session or per admin-defined duration.
- Rule: pay after verified session completes.
- Proof: session record, duration, client approval.
- Risk: abuse, unsafe content, harassment, adult content issues.
- Controls: verified clients, code of conduct, reporting, moderation, age gate if required, strict terms.

12. Product affiliate commissions

- Suggested reward: fixed amount or percentage.
- Rule: pay after purchase is confirmed and reversal window passes.
- Proof: product purchase record.
- Risk: self-purchase loops and refund abuse.
- Controls: reversal window, fraud checks, one commission per valid purchase.

13. Referral activation bonus

- Suggested reward: fixed amount or percentage of activation fee.
- Rule: pay after referred account activation clears.
- Proof: activation payment record.
- Risk: fake accounts, circular referrals.
- Controls: phone uniqueness, device/IP checks, pending period, payout caps.

15. M-PESA DEPOSITS
-------------------

Deposit methods:

- STK Push: best guided flow.
- C2B PayBill/Till: fallback/manual style flow.

STK Push flow:

1. User enters phone and amount or selects activation/recharge.
2. System creates MpesaPayment with status INITIATED.
3. System calls Daraja STK Push.
4. System stores MerchantRequestID and CheckoutRequestID.
5. User sees "check your phone".
6. Safaricom sends callback.
7. System checks ResultCode.
8. If success, system extracts receipt, amount, phone, transaction date.
9. System validates amount and account reference.
10. System posts wallet/activation ledger entry exactly once.
11. System marks payment SUCCESS.

C2B flow:

1. Admin registers validation and confirmation URLs with Safaricom.
2. User pays to PayBill/Till using account number.
3. Safaricom calls validation URL.
4. System accepts only valid account references and expected amount rules.
5. Safaricom calls confirmation URL.
6. System stores receipt and posts ledger entry exactly once.

Required safeguards:

- Unique MpesaReceiptNumber.
- Unique CheckoutRequestID where applicable.
- Store raw callback JSON.
- Return success response to Safaricom for duplicate confirmations that were already processed.
- Do not crash on callback errors.
- Add reconciliation command to compare M-Pesa records with internal payment records.


16. M-PESA WITHDRAWALS
----------------------

Withdrawal methods:

- B2C automated payout after Safaricom approval.
- Manual M-Pesa payout as fallback.

Withdrawal request flow:

1. User enters amount and confirms phone.
2. System checks user is active, not flagged, KYC rules pass, and amount >= minimum withdrawal.
3. System checks available wallet balance.
4. System checks platform safe withdrawal pool.
5. System creates WithdrawalRequest.
6. System moves requested amount from available balance to locked/pending withdrawal.
7. Admin reviews queue.
8. Admin approves or rejects.
9. If B2C is enabled, system sends B2C request.
10. System waits for result callback.
11. On success, mark PAID and post WITHDRAWAL_PAID ledger entry.
12. On failure, release amount back to available balance.

Withdrawal statuses:

- REQUESTED
- UNDER_REVIEW
- APPROVED
- PROCESSING
- PAID
- FAILED
- REJECTED
- CANCELLED

Withdrawal blocking rules:

- User available balance below minimum withdrawal.
- User amount above daily limit.
- User account is locked, flagged, suspended, or KYC-blocked.
- Phone number is missing or invalid.
- Duplicate pending withdrawal exists if admin chooses one-at-a-time rule.
- Platform safe withdrawal pool is insufficient.
- Payouts globally disabled by admin.


17. SOLVENCY AND REVENUE DASHBOARD
----------------------------------

The admin dashboard must protect the business from bankruptcy.

Definitions:

Confirmed cash:

- M-Pesa deposits that have been confirmed.
- Bank cash entered by admin.
- Other verified platform cash.

User liability:

- Sum of available user balances.
- Sum of locked balances that may become withdrawable.
- Sum of pending withdrawals.
- Sum of pending approved rewards not yet released.
- Any refundable activation credits.

Platform revenue:

- Fees explicitly earned by the platform.
- Product margins.
- Client-funded job campaign revenue.
- Real ad revenue received.
- Other non-refundable revenue recognized according to terms.

Platform expenses:

- Job rewards.
- Referral bonuses.
- Product commissions.
- M-Pesa transaction fees.
- Hosting and operating costs.

Suggested dashboard formulas:

Total wallet liability =
available_balance + pending_withdrawals + withdrawable_locked_balance + approved_pending_rewards

Current reserve surplus =
confirmed_cash - total_wallet_liability - admin_minimum_cash_buffer - estimated_mpesa_fees

For each withdrawal request, evaluate the after-payment state:

cash_after_payout =
confirmed_cash - requested_amount - estimated_mpesa_fee

liability_after_payout =
total_wallet_liability - requested_amount

required_cash_after_payout =
(liability_after_payout * reserve_ratio_target) + admin_minimum_cash_buffer

Reserve ratio =
confirmed_cash / total_wallet_liability

Withdrawal should be allowed only if:

- user_available_balance >= requested_amount
- requested_amount >= minimum_withdrawal_amount
- cash_after_payout >= required_cash_after_payout
- user and platform payout status are valid

The dashboard can also show an estimated safe withdrawal capacity by simulating approved withdrawals in priority order and stopping when the after-payment reserve rule would fail.

Dashboard warning levels:

- Green: reserve ratio >= 1.25
- Yellow: reserve ratio >= 1.00 and < 1.25
- Red: reserve ratio < 1.00

If red, admin should pause withdrawals, pause bonuses, pause high-cost jobs, or inject cash before approving more payouts.

20. BACKGROUND TASKS
--------------------

The user requested Python threading if safe.

Threading is safe only for short, non-critical, idempotent work such as:

- Sending a non-essential notification after the database transaction commits.
- Warming a small cache.
- Logging a non-financial event.

Threading is not safe for:

- Posting wallet rewards.
- M-Pesa callbacks.
- Withdrawal payouts.
- Reconciliation.
- Job reward approval.
- Anything that must survive dyno restarts.

Recommended production background options:

- Celery with Redis and a Heroku worker dyno.
- RQ with Redis and a Heroku worker dyno.
- A database-backed task table plus a management command run by Heroku Scheduler.
- Django management commands for reconciliation and cleanup.

Minimum background commands:

- expire_old_job_claims
- release_pending_referral_bonuses
- release_pending_job_rewards
- reconcile_mpesa_payments
- retry_failed_notifications
- calculate_daily_finance_snapshot


21. SECURITY DESIGN
-------------------

Application security:

- DEBUG=False in production.
- Strong SECRET_KEY from env.
- ALLOWED_HOSTS configured.
- HTTPS only in production.
- SESSION_COOKIE_SECURE=True.
- CSRF_COOKIE_SECURE=True.
- SECURE_SSL_REDIRECT=True behind Heroku proxy settings.
- Password validation enabled.
- Login rate limiting.
- Admin URL protected and monitored.

Payment security:

- All M-Pesa credentials in env vars.
- No secrets committed to Git.
- Store raw callback JSON but avoid logging secrets.
- Idempotency keys on all payment processing.
- Confirm amount before crediting wallet.
- Confirm account reference before activation.
- Do not trust frontend success messages.
- Reconciliation report for finance admin.

Wallet security:

- DecimalField for money.
- Immutable ledger entries.
- Admin adjustment requires reason.
- Audit every finance setting change.
- Lock rows during balance updates.
- Prevent negative balances unless explicitly designed and audited.

Fraud controls:

- Unique phone number.
- Device fingerprint where legally acceptable.
- IP pattern checks.
- Referral loop detection.
- Daily earning limits.
- Duplicate proof detection.
- Impossible completion time checks.
- Manual review queue.

26. TESTING REQUIREMENTS
------------------------

Critical tests:

- Login by username, phone, and email.
- Locked users cannot access jobs or withdrawals.
- Activation payment callback activates user exactly once.
- Duplicate M-Pesa callback does not double-credit wallet.
- Referral bonus posts once.
- Job worker limit cannot be exceeded under concurrency.
- User cannot claim same job twice if not allowed.
- Reward approval posts once.
- Withdrawal is blocked below minimum amount.
- Withdrawal is blocked when platform safe pool is insufficient.
- Failed B2C payout releases locked funds.
- Admin adjustment requires reason and audit log.

Recommended tooling:

- Django TestCase for models/services.
- pytest-django if preferred.
- Factory Boy for fixtures if the project grows.
- Playwright only if deep UI regression testing becomes necessary.


27. FINAL DESIGN DECISIONS
--------------------------

- Use function-based views, but keep finance logic in services.
- Use a custom user model from day one.
- Use a wallet ledger, not direct balance edits.
- Treat activation credits as liabilities unless clearly non-withdrawable.
- Use database transactions for all money and job slot operations.
- Use M-Pesa callbacks and reconciliation, not frontend responses, as source of truth.
- Prefer real background workers for financial tasks.
- Make admin settings powerful but audited.
- Make mobile UX the default experience.
- Keep rewards admin-configurable but financially guarded.
